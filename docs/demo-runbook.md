# Scout demo and frontend deployment

This walkthrough uses B's dashboard with A's persisted, draft-only worker. Follow the [dashboard–worker contract](hackathon-contract.md) for exact states and mutation semantics.

## Before the live walkthrough

1. A provisions a password for the seeded demo owner, or explicitly moves the worker/profile to an existing authenticatable owner. Sign in through `/auth/login`; never bypass it. The handoff names `scout-demo@example.com`, but current login availability has not been verified by B.
2. Configure the two public frontend Supabase variables from `frontend/.env.example`. Keep backend database, Google and model-provider credentials out of frontend hosting.
3. A confirms migrations and owner data are present and scopes worker processing to the intended owner. The current worker shares one local Gmail account across profiles; it must not be used for an open multi-user demo in that state.
4. Run `npm run dev:web` from the repo root. Sign in and open `/dashboard`. A owns worker startup and any paid enrichment runs; B does not start them automatically during UI verification.

## Five-minute narrative

1. **What arrived:** open All listings. Show the original listing link, recorded budget/bedroom match and match reason. An unmatched arrival is separate from an active pursuit.
2. **What needs you:** open a no-contact pursuit. Show the preserved stage and blocker. Supply a broker contact only when the owner authorizes the actual address; name and source are optional. Explain that the worker uses this contact directly to prepare outreach.
3. **What saved:** submit Use this contact. A failed or stale save stays visible; refresh before retrying an uncertain result. A confirmed save removes the blocker after server revalidation and leaves the pursuit matched, ready for a later worker cycle. No email was sent by the dashboard.
4. **What Scout produced:** A runs its approved draft-only cycle. Use Refresh inbox, open Conversation and show **Draft · Not sent**, recipients, subject and text. An existing draft is not regenerated by clearing a blocker or refreshing. Missing/malformed draft content is shown as unavailable.
5. **What you control:** pause/resume and close a pursuit. Explain that these affect future cycles and do not cancel already-running work. Closed rows leave Active and appear in Closed. There is no live restore button.
6. **What is still pending:** show one explicit blocker placeholder or unknown tour/calendar detail. Availability can be edited, but it does not resolve a current no-fitting-slot blocker until the worker consumer exists.

Do not use a fabricated broker address on a real pursuit to demonstrate a send. The public `/` route remains available with fictional listings for interaction rehearsals. A signed-in user's preferences there are real, even though its listings are fictional.

## Frontend deployment preparation

The repo has no hosting project configured. Choose an existing target before publishing. The production runtime must support Next.js Server Actions, session cookies and dynamic server rendering; this app is not a static export.

From the repository root:

```sh
npm ci
yarn lint
yarn test
npm run typecheck -w frontend
npm run build -w frontend
npm run start -w frontend
```

Root `yarn lint` is currently missing; targeted frontend lint is used alongside the known full-lint findings recorded in context.md. The frontend workspace is `frontend/`; build output is `frontend/.next`. Configure the two public Supabase variables on the hosting target, then configure the resulting site URL and permitted authentication callback URLs in Supabase. Do not copy root `.env`, `token.json`, Google credentials, or cached mailbox data into the frontend deployment.

After deployment, verify anonymous `/dashboard` redirects to login, the demo owner sees only its records, reload preserves a confirmed profile/command change, a stale write returns an error, and mobile controls remain usable. Verify deployed RLS with authorized test accounts/data only after A resolves worker owner scoping. Record the actual deployment URL and verified results in context.md; none is claimed by this runbook.
